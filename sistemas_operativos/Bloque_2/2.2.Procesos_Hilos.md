# Procesos. Hilos

## 1.- Introducción.

El modelo tradicional de proceso concibe cada proceso como un programa en ejecución con un **único** hilo de control. Este moodelo presenta dos limitaciones importantes:

1. **Falta de paralelismo interno**: Muchas aplicaciones necesitan ejecutar varias tareas independientes entre sí pero que comparten el mismo aspecto de direcciones y los mismos recursos.
2. **Infrautilización de multiprocesadores**: Un proceso tradicional solo puede ejecutarse en un procesador a la vez. Para aprovechar varios procesadores, la aplicación tendría que crear varios procesos distintos y repartirlos entre ellos, lo cual obliga a resolver de forma costosa cómo esos procesos comparten memoria y recursos y cómo se sincronizan entre sí.

### La solución: el hilo (thread)

Estas limitaciones se resuelven separando del proceso dos ideas que el modelo clásico tenía fundidas en una sola: la _profundidad de los recursos y la ejecución_. Así nace el **hilo** o **hebra** y con él los sistemas operativos multihilo.

Un **hilo** es una traza o secuencia de control dentro de un proceso las instrucciones de un proceso de forma independiente. Se describe por su **pila y bloque de control de
hilo** en el que se almacena su **identificación, estado de ejecución y contexto de
ejecución**.

El **proceso** pasa a ser la unidad que posee los recursos: espacio de direcciones, archivos abiertos, etc.

Un mismo proceso puede contener varios hilos, todos ellos compartiendo el espacio de direcciones y los recursos del proceso, pero cada uno con su propio flujo de ejecución.

### Descripción de un hilo:

- Tiene su **pila** (stack) propia.
- Tiene su **bloque de control de hilo**, que almacena:
  - identificación del hilo,
  - estado de ejecución,
  - contexto de ejecución

Es decir, un hilo tiene lo mínimo necesario para poder ejecutarse y ser planificado de forma independiente, pero no duplica los recursos del proceso (memoria, ficheros, etc), que siguen siendo compartidos por todos los hilos del proceso.

## 2.- Motivación

Cuando una aplicación necesita ejecutar varias tareas concurrentes usando únicamente procesos, aparecen varias desventajas claras:

- **Sobrecarga de creación elevada**: Crear un proceso nuevo implica invocar un `fork`, una llamada al sistema costosa: hay que duplicar el espacio de direcciones, las tablas del proceso, los descriptores de archivo, etc.

- **Comunicación entre procesos complicada**: Como cada proceso tiene su propio espacio de direcciones, los procesos no pueden simplemente compartir variables. Necesitan mecanismos explícitos de comunicación entre procesos (IPC), como el paso de mensajes o la memoria compartida, ambos más costosos y más dificiles de programar que el simple acceso a una variable común.

- **Gestión adicional del paralelismo**: Repartir los procesos entre distintas máquinas o procesadores, hacer que pasen la información entre sí, esperar a que terminen y recoger sus resultados exige trabajo extra por parte del programador y del sistema.

* **Recursos difíciles de compartir**: UNIX no ofrece un marco adecuado para compartir ciertos recursos entre procesos.

**Conclusión**: Usar múltiples procesos para lograr concurrencia solo tiene sentido cuando el beneficio de paralelizar compensa claramente el coste de crear y gestionar esos procesos. En muchos casos, ese coste es demasiado alto.

### ¿Porqué el hilo es la solución?

La abstracción de proceso resulta inadecuada para la computación paralela, especialmente en el caso de que las distintas unidades de ejecución:

- tengan relativamente pocas interacciones entre sí, y
- por tanto necesiten poca sincronización.

Para estos casos se necesita una abstracción más ligera: el **hilo**.

### Proceso tradicional vs. Hilo

- El **proceso UNIX** tradicional es de un único hilo: toda su computación está serializada dentro de esa única unidad de ejecución.
- Con el modelo multihilo, un mismo proceso puede contener **varios hilos** que se ejecutan de manera independiente pero comparten el espacio de direcciones t los recursos del proceso, evitando asi la sobrecarga de `fork` y la necesidad de mecanismos IPC pesados para tareas que solo necesitan colaborar de forma ligera.

## 3.- Multihilo

Un proceso es una entidad compuesta la cual engloba dos conceptos distintos y potencialmente independientes entre sí:

- **Unidad que possee recursos**: Al proceso se le asigna un espacio de memoria y, ocasionalmente, otros recursos como dispositivos de E/S o ficheros.
- **Unidad a la que se asigna el procesador**: El proceso es un flujo de ejecución (traza) a través de uno o más programas. Esta ejecución se entremezcla con la de otros procesos, de forma que el proceso tiene un estado y una prioridad de expedición. Es la unidad que el SO planifica y pide.

En la mayoría de los sistemas operativos ambas características constituyen, de hecho, la esencia del proceso. Pero son **independientes**, y el SO puede tratarlas como tales.

### El thread como separación de esas dos características.

Esta distinción ha llevado a los sistemas operativos actuales a desarrollar el **thread** (hilo, hebra, o proceso ligero). Separando las dos características anteriores:

- **Hilo**: Unidad de asignación de la CPU.
- **Proceso**: Unidad que posee los recursos.

Ahora, dentro de un **proceso** puede haber **uno o más hilos de control**, cada uno con:

- Un estado de ejecución.
- Un contexto de procesador.
- Una pila de ejecución.
- Algo de almacenamiento estático por variables locales,
- Acceso a la memoria y recursos de trabajo, compartidos con los demás hilos del mismo proceso.

### Pero, ¿qué es exactamente un hilo?

Es una unidad básica de utilización de la CPU. Tiene de propio:

- identificador de hilo
- contador de programa
- conjunto de registros,
- pila

Además, comparte con los demás hilos del mismo proceso:

- la sección del código
- la sección de datos
- otros recursos del SO

En el modelo multihilo, el proceso conserva un único bloque de control de proceso y un único espacio de direcciones de usuario, pero cada hilo tiene su propio bloque de control de hilo y su propio par de pilas.

### Beneficios de los hilos

- Se tarda **menos tiempo** en crear un hilo nuevo dentro de un proceso ya existente que en crear un proceso nuevo.

- Tambien se tarde menos en **terminarlo**.

- El **cambio de contexto entre hilos** del mismo proceso es más rápido que entre procesos distintos.

- Al tener varios flujos de ejecución dentro del mismo proceso, se mantiene **una máquina copia en memoria del código**, el lugar de varias.

Un ejemplo de aplicación que podría hacer uso de los hilos es **un servidor de ficheros de una red de área local**.

Un servidor de ficheros de una red de área local puede generar un nuevo hilo cada vez que llega una solicitud sobre un fichero. Como el servidor atiende muchísimas solicitudes, se crean y destruyen numerosos hilos en poco tiempo. Si el servidor es un multiprocesador, varios hilos del mismo proceso pueden ejecutarse simultaneamente en distintos procesadores.

| Procesos                                                                             | Hilos (Threads)                                                       |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Al cambiar de proceso se requieren recursos del sistema operativo                    | No se requieren recursos del SO para el cambio de hilos               |
| Si un proceso se bloquea, se detiene por completo; no se puede ejecutar parte de él. | Si un hilo se bloquea, otro hilo del mismo puede seguir ejecutándose  |
| Cada proceso usa el mismo código pero tiene su propia memoria                        | Todos los hilos pueden compartir archivos y procesos hijos            |
| Una aplicación con múltiples procesos usa más recursos del sistema                   | Los procesos con múltiples hilos consumen menos recursos del sistema. |
| Cada proceso funciona de manera independiente                                        | Los hilos pueden acceder a los datos de otros hilos                   |

## 4.- Concurrencia y paralelismo

Es muy importante saber diferenciar entre **concurrencia** y **paralelismo**:

- **Paralelismo**: Es una aplicación multiprocesador, es el **grado real** de ejecución paralela alcanzado. Está limitado por el número de **procesadores físicos** disponibles para la aplicación. Es, por tanto, lo que realmente ocurre en el hardware.

* **Concurrencia**: Es el **máximo paralelismo** que la aplicación podría alcanzar si dispusiera de un número ilimitado de procesadores. No depende del hardware, sino cómo esté escrita la aplicación y de cuántos hilos de control puedan ejecutarse simultáneamente. Es, por tanto, una propiedad del diseño de la aplicación, no de la máquina donde corre.

En conclusión: la concurrencia es el potencial del paralelismo que ofrece el programa, el paralelismo no es la parte de ese potencial que realmente se materializa según el hardware disponible.

La concurrencia se puede suministrar en 2 niveles:

1. **Concurrencia de sistema (a nivel de kernel)**:
   - La proporciona el **kernel**, que reconoce múltiples hilos de control de un proceso llamados tambien **hilos calientes** y los planifica de forma independiente.
   - El kernel **multiplexa** esos hilos entre los procesadores disponibles.
   - En este caso, además del BCP (Bloque de control de proceso), existe un **Bloque de control de hilo (BCH)** por cada hilo del proceso.
   * Ventaja incluso en monoprocesador: si un hilo se bloquea esperando un suceso o recurso, el kernel puede planificar otro hilo del mismo proceso para que siga avanzando.

2. **Concurrencia del usuario (a nivel de aplicacion)**:
   - La proporciona la propia **aplicacion**, mediante bibliotecas de hilos a nivel de usuario.
   - Estos hilos de usuario, tambien llamados **corrutinas** o **hilos frios**, no son reconocidos por el kernel sino que es la propia aplicación que debe planificarlos y gestionarlos.
   - **No suministra concurrencia ni paralelismo reales** porque no pueden ejecutarse en paralelo entre sí.
   - Su valor está en que ofrecen un **modelo de programación natural** para escribir aplicaciones concurrentes.
   - Con llamadas al sistema no bloqueantes, la aplicación puede mantener varias "iteraciones" en curso a la vez. Los hilos de usuario **simplifican** esto guardando el estado de cada iteración en **variables locales por hilo**, en lugar de tener que mantener una tabla de estado global por todas las iteraciones

### Limitaciones de cada modelo por separado

Los hilos se usan tanto como herramienta de organización del código como para explotar varios procesadores, pero cada enfoque puro tiene un valor limitado:

- **Hilos de kernel**: permiten ejecución paralela real sobre multiprocesadores, pero **no son aconsejables** para estructurar aplicaciones que necesitan crear muchísimos hilos.
- **Hilos de usuarios puros**: son útiles solo para estructurar la aplicación (organizar el código de forma concurrente), pero **no permiten ejecución paralela real** del código, porque el kernel no los ve como unidades independientes.

La solución a estas limitaciones en un modelo de **concurrencia mixto**.
Muchos sistemas combinan ambos niveles:

- El **kernel** reconoce múltiples hilos dentro de un proceso .
- La **biblioteca de usuario** añade hilos de usuario adicionales que el kernel no ve, normalmente montados sobre los hilos de kernel.

Las ventajas de este modelo mixto son:

- Los hilos de usuario permiten sincronizar rutinas concurrentes del programa **sin la sobrecarga de hacer llamadas al sistema**.
- Son deseables incluso en sistmas cuyo núcleo no soporta multihilo.
- Además, dividir la funcionalidad de soporte de hilos entre el kernel y la biblioteca de usuario es coherente con el principio general de **reducir el tamaño y la responsabilidad del kernel**

## 5.- Modelos multihilo

Existen dos grandes categorias para implementar hilos:

- **ULT (User Level Thread)**: hilos a nivel de usuario. Son los que usamos al programar, y pueden crearse desde lenguajes como Java.
- **KLT (Kernel Level Thread)**: hilos a nivel de kernel de núcleo o sistema. Pertenecen al propio SO y pueden dar soporte a los hilos de usuario.

### 5.1 Hilos a nivel de usuario

En una aplicación **ULT** pura, **toda** la gestión de hilos la hace la propia aplicación: el **núcleo no sabe que existen hilos**, solo ve el proceso como un todo.

#### Cómo funciona:

- La aplicación se programa como multihilo usando una **biblioteca de hilos**, que ofrece todas las funciones necesarias: crear, sincronizar, planificar y manejar hilos, sin ayuda especial de kernel
- Como las interacciones entre hilos no involucran kernel, son **muy rápidas**.
- Por defecto, una aplicación arranca con un único hilo, dentro de un único proceso gestionado por el núcleo.
- Cuando ese hilo crea un nuevo hilo, es la **biblioteca de hilos** la que hace la creación:
  1. El flujo de control pasa a la biblioteca mediante una llamada a procedimiento.
  2. La biblioteca crea la estructura de datos del nuevo hilo.
  3. Cede el control a un hilo del proceso que esté en estado Preparado/Listo , elegido según algún algoritmo de planificación
  4. Al pasar el control a la biblioteca se salva el contexto del hilo actual, se restaura cuando el control vuelve del hilo a la biblioteca.

- La biblioteca actúa, en la práctica, como un pequeño **kernel en miniatura** para los hilos que controla.

- Todo esto ocurre en **espacio de usuario y dentro del mismo proceso**. El núcleo sigue siendo el único responsable de la conmutación _entre_ procesos porque solo él tiene privilegio para modificar los registros de gestión de memoria.

#### Los ULT no son planificables por el kernel.

- El kernel **no conoce** los hilos de usuario; simplemente planifica el proceso base, y es este, mediante la biblioteca, quien por turnos planifica sus propios hilos internamente.
- Si el proceso es apropiado (expulsado), lo son también todos sus hilos.
- Si un hilo de usuario hace una** llamada al sistema bloqueante**, esta bloquea al proceso base completo, y por tanto **se bloquean todos los hilos** de ese proceso.

Evidentemente, estos tienen sus ventajas:

- No hace falta cambiar a modo núcleo para intercambiar hilos, ya que todas las estructuras están en espacio de usuario del mismo proceso → mejora el rendimiento.

- Se puede definir una **planificación específica para cada aplicación**

- Se pueden ejecutar sobre **cualquier sistema operativo**, sin necesidad de modificar su núcleo.

al igual que tiene sus desventajas:

- La mayoría de llamadas al sistema son bloqueantes: si un hilo se bloquea, **se bloquean todos los hilos** del proceso.
- En sistemas con **varios procesadores**, no se puede aprovechar esta ventaja: el núcleo asigna un proceso a un único procesador cada vez, así que los hilos de un mismo proceso **no pueden ejecutarse en paralelo.**

Una forma de superar el bloqueo de hilos es mediante la técnica **jacketing**:

- Consiste en convertir una llamada bloqueante en no bloqueante.
- En vez de invocar directamente la llamada al sistema, se llama a una función de recubrimiento de la aplicación.
- Esta función comprueba de antemano si la llamada va a bloquear el hilo:
  - si es así, pasa el hilo a estado Preparado y cede el control a otro hilo, evitando así bloquear a todo el proceso.

### 5.2 Hilos a nivel de Kernel

En una aplicación **KLT pura**, la gestión de los hilos la realiza el kernel directamente:

- Todos olos hilos de la misma aplicación perteecen a un único proceso
- El núcleo mantiene la información de contexto **tanto el proceso como un todo, como de cada hilo** dentro de el.
- El **núcleo planifica los hilos**.
- Las propias funciones del núcleo puede ser multihilo.

#### Consecuencias

- Los hilos pueden hacer llamadas al sistema y bloquearse por E/S o por recursos de **forma individual**: si un hilo se bloquea, no arrastra el resto de hilos del proceso, que puedan seguir ejecutandose.

- En un sistema **multiprocesador**, el proceso sí puede disfrutar de **verdadero paralelismo**: cada hilo puede despacharse a un procesador distinto y ejecutarse simultaneamente.

Estos, al igual que los ULT, tienen sus limitaciones como:

- Crear, destruir y sincronizar hilos requiere **llamadas al sistema**, que son relativamente costosas porque:
  - cada llamada implica **dos cambios de nodo**,
  - en cada cambio de modo el hilo cruza un **dominio de protección**
  - el kernel debe **copiar y validar** los parámetros de la llamada desde el espacio de usuario al del kernel
  - de igual forma, al retornar, debe copiar los datos de vuelta al espacio de usuario
- Cuando los hilos acceden **freuentemente a datos compartidos**, la sobrecarga de sincronización puede anular la ganancia de rendimiento:
  - la mayoría de sistemas multiprocesador ofrecen **cerrojos** adquiribles a nivel de usuario si no están bloqueados por otro hilo.
  - si el recurso no está disponible, el hilo puede hacer **espera ocupada**, sin intervención del kernel.
  - si el bloqueo va a ser largo, es preferible bloquear el hilo, lo cual si requiere intervención del kernel y, por tanto, tiene más coste.

### 5.3 Planificación de hilos

Algunos SO combinan ambos niveles: la creación de hilos y la mayor parte de su planificación/sincronización se hace en espacio de usuario, y los múltiples ULT de una aplicación se asocian con varios KLT.

Estos sistemas introducen el concepto de **procesador lógico**: los hilos de usuario se ejecutan sobre procesadores lógicos, dando lugar a una planificación en **dos niveles**.

1. Asignar los hilos de usuario a los procesadores lógicos.
2. Asignar los procesadores lógicos al procesador o precesadores físicos.

Las técnicas de correspondencia entre hilos y procesadores lógicos se describen a partir de la relación **Threads:Processes**:

| Relacion | Descripción                                                                                                                    | Ejemplo de sistemas                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| **1:1**  | Cada hilo de ejecución es un proceso único con su propio espacio de direcciones y recursos                                     | Implementaciones tradicionales de UNIX         |
| **M:1**  | Un proceso define un espacio de direcciones y la propiedad dinámica de recursos; dentro de él se crean y ejecutan varios hilos | Windows NT, Solaris, Linux, OS/2, OS/390, MACH |
| **1:M**  | Un hilo puede migrar de un entorno de proceso a otro, lo que le permite moverse fácilmente entre sistemas distintos            | Ra (Clouds), Emerald                           |
| **M:N**  | Combina atributos de M:1 y 1:M                                                                                                 | TRIX                                           |

A partir de esto, se identifican tres técnicas concretas de planificación de hilos de usuario sobre recursos del núcleo (las CPUs):

#### a) Muchos hilos en un procesador lógico - Modelo Muchos a uno

![procesos1](/sistemas_operativos/assets/procesos1.png)

- Todos los hilos creados en espacio de usuario **compiten** por ejecutarse en el **único ** procesador lógico asignado a ese proceso.
- El proceso **no se beneficia** de tener varios procesadores físicos.
- Una llamada bloqueante **bloquea todo el proceso**.
- A cambio, la creación de hilos y su planificación se hacen en espacio de usarlo sin sumar recursos del núcleo -> es **más rápido**
- Corresponde al "proceso 1" en el esquema de planificación de Solaris.

#### b) Un hilo por procesador lógico — modelo Uno-a-Uno

![proceso2](/sistemas_operativos/assets/procesos1.png)

- Se asigna un procesador lógico a cada hilo de usuario.
- Muchos hilos pueden ejecutarse simultáneamente en diferentes procesadores físicos.
- Sin embargo, crear un hilo implica crear un procesador lógico, es decir, una **llamada al sistema**.
- Como cada procesador lógico consume recursos del núcleo, el número de hilos que se **pueden crear está limitado**.
- Lo usan MVJ (máquinas virtuales Java) basadas en bibliotecas como Win32, OS/2, o LinuxThreads.
- Corresponde al "proceso 2" del esquema.

#### c) Muchos hilos en muchos procesadores lógicos — modelo Muchos-a-Muchos (estricto)

![procesos3](/sistemas_operativos/assets/procesos1.png)

- Un número de hilos se multiplexa sobre un número de procesadores lógicos **igual o menor**.
- Muchos hilos pueden ejecutarse en paralelo en distintas CPUs.
- Las llamadas al sistema bloqueantes no bloquean a todo el proceso, solo al hilo implicado.
- Corresponde al "proceso 3" del esquema.

#### d) El modelo de dos niveles — Muchos-a-Muchos (no estricto)

- Igual que el anterior, pero añade la posibilidad de **enlazar** (bind) un hilo específico a un procesador lógico concreto.
- Se considera probablemente el **mejor modelo**.
- Lo usan sistemas como Digital UNIX, Solaris, IRIX, HP-UX, AIX.
- En el caso de Java, las MVJ sobre estos sistemas pueden elegir libremente cualquier combinación de hilos enlazados o no enlazados: la elección del modelo de hilos es una decisión de implementación de quienes programan la MVJ (Java en sí mismo no tiene el concepto de procesador lógico).
- Corresponde al "proceso 4" del esquema.

## 6.- Bibliotecas de hilos

Una biblioteca de hilos proporciona al programador una **API** para crear y gestionar hilos. Existen dos formas principales de implementarla:

- **En espacio de usuario**: no hay soporte del sistema operativo. El código y las estructuras de datos de la biblioteca residen en espacio de usuario. Invocar una función de la biblioteca equivale, simplemente, a una **llamada de función** normal.

* **En espacio del kernel**: el código y las estructuras de datos de la biblioteca están en espacio de kernel. Invocar una función de la **API** provoca, en este caso, una **llamada al sistema**.

### 6.1 Pthreads

Es la extension de hilos del estándar **POSIX**. Es importante remarcar que es una **especificación, no una implementación**: cada sistema operativo la implementa como considera oportuno.

#### Ejemplo: Programa multihilo que calcula un sumatorio

Un ejemplo típico es un programa en C que calcula el sumatorio de un entero no negativo usando un hilo adicional:

- El programa arranca con una única hebra de control `main()`.
- Tras las inicializaciones, `main()` crea un segundo **hilo**, que empieza a ejecutar la función `runner()`.
- Ambos hilos **comparten la variable global `sum`**, donde se acumula el resultado.

#### Elementos del código

- Todo programa que use Pthreads debe incluir la cabecera `pthread.h`.
- `pthread_t tid` declara el identificador del hilo.
- `pthread_attr_t attr` declara los **atributos** del hilo.
- `pthread_create(...)` crea el nuevo hilo. Se le pasan como parámetros:
  1. el identificador del hilo (tid)
  2. los atributos (atrr)
  3. el nombre de la función que ejecutará el nuevo hilo (`runner`)
  4. el parametro de entrada para esa función
- `pthread_join(...)` el hilo padre la invoca para **esperar** a que el hilo creado **termine** antes de continuar.
