# 4.3 Hiperpaginación (Thrashing)
Cuando el número de marcos asignados a un proceso desciende por debajo del mínimo requerido por la arquitectura de la CPU, el sistema debe suspenderlo y liberar sus marcos. Si un proceso no dispone de marcos suficientes para sus páginas activas, expulsará continuamente páginas que volverá a necesitar de inmediato

Se define la **hiperpaginación (thrashing)** como un estado de altísima actividad de reemplazo donde el sistema dedica más tiempo a transferir páginas de/hacia el disco que a ejecutar instrucciones útiles

```text
Uso de CPU (%)
   ▲
   │         Cúpula de máxima eficiencia
   │            ┌───────────┐
   │           /             \  ◄── Colapso por Hiperpaginación (Thrashing)
   │          /               \
   │         /                 \
   │        /                   \
   └───────┴─────────────────────┴───────────────────► Grado de Multiprogramación
```

## 4.3.1 Causas del Colapso por Hiperpaginación
La causa principal reside en el uso de un reemplazo global de páginas combinado con la **realimentación positiva del planificador de la CPU**:

1. **Caída del Uso de CPU:** Un proceso entra en una nueva fase de ejecución y exige más marcos. Empieza a fallar y a arrebatar marcos a otros procesos
2. **Bloqueo masivo en Cola de E/S:** Los demás procesos pierden sus páginas activas y también generan fallos, saturando la cola del dispositivo de swap. La lista de procesos listos se vacía y el uso de la CPU se desploma
3. **Reacción errónea del SO:** El planificador observa la baja utilización de la CPU y aumenta el grado de multiprogramación introduciendo un nuevo proceso
4. **Retroalimentación:** El nuevo proceso requiere marcos y agrava la falta de espacio, desencadenando el colapso definitivo del sistema

> **Solución parcial:** El reemplazo local o por prioridades limita el impacto impidiendo que un proceso robe marcos a otro. Sin embargo, la saturación del canal de E/S termina degradando el tiempo efectivo de acceso (EAT) de todo el sistema

## 4.3.2 El Principio de Localidad
Para evitar el thrashing, el sistema operativo debe proveer a cada proceso el número exacto de marcos que su **localidad actual** exige

```text
Espacio de Direcciones
    ┌──────────────────────┐
    │  Subrutina / Código  │ ──┐
    ├──────────────────────┤   ├── Localidad Actual (Páginas usadas conjuntamente)
    │  Variables Locales   │ ──┘
    ├──────────────────────┤
    │  Estructura Datos    │ ─── Localidad Futura
    └──────────────────────┘
```

* **Localidad:** Conjunto de páginas que un proceso utiliza de forma conjunta durante un intervalo de tiempo. Viene determinada por la estructura del programa (rutinas, bucles, arreglos)
* **Regla de asignación**: Si los marcos asignados $a_i < \text{tamaño de la localidad}$, se desencadena hiperpaginación. Si $a_i \ge \text{tamaño de la localidad}$, los fallos de página cesan tras la fase de carga inicial

## 4.3.3 Modelo del Conjunto de Trabajo (Working Set Model)
El modelo del Conjunto de Trabajo aproxima la localidad del proceso monitorizando una ventana temporal fija de $\Delta$ referencias a memoria

```text
Ventana del Conjunto de Trabajo (Δ referencias)
┌─────────────────────────────────────────────────────────┐
│  ... 2  6  1  5  7  7  7  7  5  1  │  3  4  3  4  4  ...│
└────────────────────────────────────┴────────────────────┘
                  t1                               t2
     WSS(t1) = {1, 2, 5, 6, 7}               WSS(t2) = {3, 4}
```
### Parámetros Principales
* **$\Delta$ (Ventana de referencias):** Define el horizonte de análisis. Si es muy pequeño no abarca la localidad completa; si es muy grande solapa varias localidades.
* **$WSS_i$ (Working Set Size):** Número total de páginas distintas referenciadas en la ventana $\Delta$ por el proceso $p_i$.
* **Demanda Total ($D$)**:
$$D = \sum WSS_i$$

### Criterio de Control del SO
* **Si $D \le m$ (Marcos libres disponibles):** Hay suficiente memoria. Se pueden admitir nuevos procesos.
* **Si $D > m$:** Se provocará hiperpaginación. El sistema operativo suspende a un proceso completo (swapped out) y distribuye sus marcos entre los procesos restantes.

### Aproximación Hardware (Cronómetro + Bits de Referencia)
Monitorear cada acceso a memoria para actualizar el conjunto activo es inviable por software. 
Se aplica una aproximación periódica:
* Se lanza una interrupción de reloj cada cierto número de accesos (ej. $5.000$)
* Se guardan y limpian los bits de referencia hardware de cada página
* Si una página conserva al menos un bit a `1` en la secuencia de históricos, pertenece al conjunto activo

## 4.3.4 Control por Frecuencia de Fallos de Página (PFF)
La estrategia de **Frecuencia de Fallos de Página (Page-Fault Frequency - PFF)** ofrece una alternativa directa al medir el rendimiento del proceso

```text
Tasa de Fallos
   ▲
   │    ZONA DE AUMENTO DE MARCOS
   │  ------------------------------ Límite Superior (Asignar marco extra)
   │
   │    ZONA DE ESTABILIDAD
   │  ------------------------------ Límite Inferior (Quitar marco sobrante)
   │    ZONA DE LIBERACIÓN
   └─────────────────────────────────────────► Tiempo
```

### Regla de Control
1. **Tasa de Fallos $>$ Límite Superior:** El proceso necesita más marcos; se le asigna un marco libre disponible
2. **Tasa de Fallos $<$ Límite Inferior:** El proceso tiene marcos sobrantes; se le retira un marco para reasignarlo
3. **Ausencia de Marcos Libres:** Si un proceso supera el límite superior pero la memoria física está llena ($m$), se suspende el proceso y se redistribuyen sus marcos

### Cuadro Comparativo de Estrategias para Prevenir el Thrashing
| Criterio | Modelo del Conjunto de Trabajo (Working Set) | Frecuencia de Fallos de Página (PFF) |
| :--- | :--- | :--- |
| **Métrica de Control** | Número de páginas únicas en ventana $\Delta$ ($WSS_i$). | Tasa directa de fallos de página por unidad de tiempo. |
| **Enfoque** | **Preventivo** (Estima la localidad antes del fallo). | **Reactivo** (Ajusta marcos tras medir fallos). |
| **Sobrecarga (Overhead)** | **Alta** (Requiere mantenimiento de bits de referencia e interrupciones). | **Baja** (Solo actúa en cada evento de fallo de página). |
| **Acción ante Escasez** | Suspende procesos completos si $\sum WSS_i > m$. | Suspende procesos si la tasa sube y no hay marcos libres. |
|

## 4.3.5 Otras Consideraciones en la Gestión de Memoria Virtual
Para completar el diseño de un sistema con memoria virtual, el sistema operativo debe considerar una serie de factores arquitectónicos y de gestión avanzada:

```text
OTRAS CONSIDERACIONES DE DISEÑO
 ├── 1. Prepaginación (Prepaging)
 ├── 2. Tamaño de Página (Page Size)
 ├── 3. Estructuras de Datos y Programación
 └─┴ 4. Bloqueo de Páginas en Memoria (Pinning / Locking)
```
### 1. Prepaginación (Prepaging)
Intenta evitar la alta tasa inicial de fallos de página que ocurre al iniciar un proceso o al reanudarlo tras ser suspendido (swapped out)

* **Mecanismo**: Trae a memoria principal, de una sola vez, la página solicitada junto con un conjunto de páginas que probablemente se necesitarán a continuación (basándose, por ejemplo, en su **Conjunto de Trabajo**)

* **Compromiso:** Si las páginas traídas por adelantado no se utilizan, se habrá desperdiciado tiempo de E/S y procesamiento. Solo es beneficiosa si el coste de la prepaginación es menor que el coste de servir los fallos de página individuales

### 2. Valoración del Tamaño de Página
La elección del tamaño de página ($S$) por parte de los diseñadores del hardware/SO implica un compromiso entre múltiples factores:

| Factor | Tamaño de Página Grande | Tamaño de Página Pequeño |
| :--- | :--- | :--- |
| **Tamaño de la Tabla de Páginas** | **Menor:** Requiere menos entradas por proceso. | **Mayor:** Ocupa mucho espacio en RAM. |
| **Fragmentación Interna** | **Mayor:** En promedio se desperdicia $S/2$ bytes en la última página de cada proceso. | **Menor:** Desperdicio mínimo en la última página. |
| **E/S de Disco** | **Más eficiente:** La transferencia por bloques grandes aprovecha el ancho de banda del canal. | **Menos eficiente:** Múltiples accesos E/S pequeños aumentan la latencia. |
| **Precisión de la Localidad** | **Menor:** Incluye código/datos no usados dentro de la misma página. | **Mayor:** Solo se traen a RAM las instrucciones estrictamente necesarias. |
|

### 3. Impacto de las Estructuras de Datos y Programación
La forma en que se codifica un programa afecta drásticamente a la tasa de fallos de página. La alineación del recorrido de los datos con el almacenamiento en memoria física es clave

#### Ejemplo de Recorrido de Matriz:
Supongamos una matriz A[128][128] almacenada por filas, donde cada fila ocupa exactamente una página de memoria.

* **Recorrido por Columnas (Mapeo ineficiente)**
```cpp
for (j = 0; j < 128; j++)
    for (i = 0; i < 128; i++)
        A[i][j] = 0;
```
Cada acceso salta a una página distinta, pudiendo provocar hasta $16.384$ fallos de página

* **Recorrido por Filas (Aprovechamiento de la Localidad):**
```cpp
for (i = 0; i < 128; i++)
    for (j = 0; j < 128; j++)
        A[i][j] = 0;
```
> Accede secuencialmente a los datos de una misma página antes de pasar a la siguiente, reduciendo la cifra a solo $128$ fallos de página

### 4. Bloqueo de Páginas en Memoria (Pinning / Frame Locking)
Existen situaciones donde ciertas páginas **nunca deben ser sustituidas** por un algoritmo de reemplazo ni expulsadas al disco:

1. **Núcleo del Sistema Operativo:** El código crítico del kernel y las estructuras de gestión de interrupciones deben residir permanentemente en RAM

2. **Buffer de E/S de Dispositivos (E/S por DMA):** Si un controlador de disco está escribiendo datos directamente mediante DMA (Direct Memory Access) en el buffer de un proceso, esa página no puede ser reemplazada. De lo contrario, la E/S sobreescribiría datos pertenecientes a un proceso totalmente distinto
