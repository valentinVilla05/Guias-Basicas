# 1.6 Llamadas al sistema y modo dual

Si un programa de usuario no puede tocar el hardware directamente, **¿cómo consigue que el sistema abra un ficher, lea el teclado o cree un proces?** La respuesta es el mecanismo más importante de la asignatura: las **llamadas al sistema**.

## 1.6.1 Servicios del sistema operativo

Antes de ver _como_ se pide algo conviene saber _qué_ se le puede pedir. Los servicios se dividen según **quien los pone en marcha**:

| **Se solicitan (llamadas al sistema)**                     | **El propio sistema los ejerce**                            |
| ---------------------------------------------------------- | ----------------------------------------------------------- |
| Ejecución de programas: cargar, ejecutar y terminar        | Detección de errores: vigilar y responder sin caerse        |
| Operaciones de E/S: leer y escribir sin conocer el aparato | Asignación y contabilidad: repartir recursos y medir su uso |
| Sistema de ficheros: crear, borrar, leer, escribir, buscar | Protección y seguridad: aislar a unos usuarios de otros     |
| Comunicaciones: entre procesos, en la máquina o por red    |

Los 4 primeros existen por **comodidad de quien programa**. Los tres últimos protegen la **eficiencia y la seguridad del propio sistema**: no tendría sentido que un programa pudiera solicitarlos ni renunciar a ellos, porque precisamente existen para acotar lo que ese programa puede hacer.

## 1.6.2 El intérprete de órdenes (shell)

Programa que lee órdenes del usuario y las ejecuta: es la interfaz de usuario textual con el sistema. **No forma parte del núcleo:** es un programa más, sustituible, que pide al sistema operativo todo lo que necesita mediante llamadas al sistema, igual que cualquier otra aplicación.

**Ciclo del intérprete**

1.  **Indicador**: muestra el simbolo de espera
2.  **Lee la orden**: que escribe el usuario
3.  **La identifica**: ¿interna o externa?
    - **Interna** (`cd`, `exit`): la resuelve el propio intérprete. No hay programa que cargar ni proceso nuevo que crear
    - **Externa** (`ls`, `cp`, `gcc`,...): es un programa del disco; hay que cargarlo con `fork` + `exec` + `wait`.
4.  **Vuelve a empezar**

#### ¿Por qué `cd` tiene que ser interna?

Una orden interna cambia el estado del propio intérprete, así que no puede delegarse en un proceso hijo: si `cd` se ejecutara en un hijo, el directorio cambiaría en el hijo y el padre seguiría donde estaba.

_Intérpretes actuales:_ `bash` y `zsh` en Linux/MacOS y `PowerShell`

## 1.6.3 Interfaz de usuario ≠ interfaz con el sistema operativo

Conviene no confundir **cómo habla el usuario** con el sistema y **cómo hablan los programas** con él: son cosas de naturaleza distinta.

|                 | Interfaz de usuario                           | Interfaz con el sistema operativo            |
| --------------- | --------------------------------------------- | -------------------------------------------- |
| Quién lo usa    | Personas                                      | Programas                                    |
| Formas          | Terminal (shell) o interfaz gráfica           | Llamadas al sistema                          |
| Para qué existe | Comodidad: que una persona pueda ordenar algo | Necesidad: el único modo de cruzar al núcleo |
| ¿Sustituible?   | Sí                                            | No                                           |

Al arrastrar un fichero a la papelera, la interfaz gráfica acaba invocando **las mismas llamasdas al sistema** que la orden `rn`. La interfaz gráfica sustituye al intérprete de órdenes, nunca a la interfaz con el sistema operativo.

## 1.6.4 La llamada del sistema por dentro

Idea clave: **el programa no salta al núcleo**. Si pudiera elegir a qué elegir a qué dirección saltar, la protección no existiría. Lo que el programa hace es ejecutar _una instrucción especial_ (`trap`),y es el **hardware** quien decide el destino, siempre el mismo.

**Los cuatro pasos**

1. El programa ejecuta `trap` con el número de llamadas en un registro
2. El hardware salva el **contexto de ejecución** (PC y PSW), activa el modo núcleo y salta a una dirección fija, establecida por el SO al arrancar
3. El núcleo consulta la **tabla de llamadas al sistema** e invoca la rutina correspondiente al número k
4. `return from trap` deja el resultado en un registro y restaura el modo usuario junto con el PC y el PSW salvados

**Contexto de ejecución**: conjunto mínimo de información que define el estado de un programa en un instante dado y que basta para reanudarlo exactamente donde se quedó. En su versión mínima son dos registros:

- **PC** (_program counter_): la instrucción siguiente
- **PSW** (_processor status word_): recoge el bit de modo y los indicadores de la última operación

#### Por qué la dirección de destino es fija

Si el programa pudiera indicar a qué dirección del núcleo saltar, bastaría con apuntar al centro de una rutina, después de sus comprobaciones con permisos, para saltarse la seguridad. Al haber **una sola entrada**, toda petición atraviesa el mismo código de verificación

```text
Ejemplo: una llamada read() vista en los registros

PASO                          PC       MODO     Nº LLAMADA   RESULTADO
0. Antes de la llamada        0x4010   usuario  —            —
1. El programa ejecuta trap   0x4010   usuario  0 (read)      —
2. El hardware salva y salta  0x8000   núcleo   0             —
3. La tabla traduce el nº     0x8420   núcleo   0             —
4. La rutina lee del disco    0x8460   núcleo   0             128
5. return from trap           0x4014   usuario  —              128

El bit de modo cambia exactamente 2 veces (pasos 2 y 5),
y ninguna de las dos la decide el programa.
```

## 1.6.5 Las dos puertas: interrupción hardware y software

Las dos comparten toda la mecánica (salto forzado, contexto salvado, rutina de tratamiento, retorno) y se diferencian en **quién la provoca y cuándo**.

|                          | **Interrupción software (_trap_)**        | Interrupción hardware (_IRQ_)                       |
| ------------------------ | ----------------------------------------- | --------------------------------------------------- |
| Quién la provoca         | El programa en ejecución, a propósito     | Un dispositivo, ajeno al programa                   |
| Cuándo ocurre            | **Síncrona**: en una instrucción concreta | **Asíncrona**: entre dos instrucciones cualesquiera |
| ¿Reproducible?           | Sí, siempre en el mismo punto             | No, cada ejecución cae en otro sitio                |
| Quién queda interrumpido | El que la pidió, y espera el resultado    | Cualquiera, y no espera nada                        |
| Para qué sirve           | Pedir un servicio al sistema operativo    | Avisar de un suceso: reloj, E/S, DMA                |

Consecuencia práctica: como la interrupción de hardware puede caer en cualquier punto, el código del núcleo ha de estar preparado para ser interrumpido en medio de lo que sea.

## 1.6.6 Las API y la portabilidad

En la práctica casi ningún programa ejecuta `trap` directamente: llama a `printf` o a `fopen`. Entre el código fuente y la llamada al sistema hay una capa intermedia, la API (interfaz de programación de aplicaciones).

- `printf()` pertenece a la **API** de C y acaba en la llamada `write()`
- Lo que se estandariza es la **API**, no la llamada al sistema en sí
- Un programa escrito contra **POSIX** compila en Linux y en macOS sin cambios (comparten API), pero **el binario no se copia de uno a otro**: lo que viaja es el código fuente
- **Win32** es la API nativa de Windows: resuelve los mismos problemas con otros nombres (`CreateFile` donde POSIX tiene `open`)

| **Categoría de llamadas** | **Ejemplos (POSIX)**             |
| ------------------------- | -------------------------------- |
| Control de procesos       | `fork`, `exec`, `wait`, `exit`   |
| Gestión de ficheros       | `open`, `read`, `write`, `close` |
| Gestión de dispositivos   | `ioctl`, `poll`                  |
| Información del sistema   | `getpid`, `time`, `uname`        |
| Comunicaciones            | `pipe`, `socket`, `send`, `recv` |

**Cruzar la frontera no es gratis.** Por eso las bibliotecas agrupan operaciones en un búfer antes de llamar al núcleo: mil `printf()` no provocan mil `write()`, sino unos pocos cruces cuando el búfer se llena. El trabajo escrito es el mismo; lo que cambia es el número de viajes al núcleo.

## 1.6.7 Modo dual y protección

El **modo dual** consiste en que el procesdor distingue al menos dos modos de ejecución mediante un **bit de modo** en la PSW:

- **Modo usuario**: Solo se ejecutan instrucciones ordinarias (sumar, comparar, saltar). Las instrucciones privilegiadas (gestionar interrupciones, cambiar de proceso, proteger memoria, E/S fisica...) provocan una excepción.

- **Modo núcleo** (supervisor): se ejecutan todas las instrucciones, sin excepción. Solo se ejecuta aquí el código del sistema operativo

El bit no es una convención del software: lo consulta el propio procesador **antes de cada instrucción**, y un programa de usuario no puede modificarlo (hacerlo es, a su vez, una operación privilegiada).

#### Sin modo dual no hay protección

El Intel 8088 del primer PC carecía de modo dual: cualquier programa de MS-DOS podía escribir donde quisiera y colapsar la máquina entera. No era un descuido del sistema operativo, sino una imposibilidad: sin apoyo del procesador, ningún software puede protegerse de otro software.

## 1.6.8 Resumen y conceptos clave

- **Servicios del SO**: unos se piden mediante llamada al sistema (E/S, ficheros, procesos, comunicaciones); otros los ejerce el sistema por su cuenta (errores, contabilidad, protección).
- **Intérprete de órdenes**: es un programa más, sustituible, que usa `fork`/`exec`/`wait` para las órdenes externas y resuelve las internas (`cd`) sin crear proceso.
- **Dos interfaces distintas:** la de usuario (sustituible: terminal o GUI) y la del sistema operativo (única, no sustituible: llamadas al sistema).
- `trap` y `return from trap`: el programa ejecuta una instrucción; es el hardware quien salva el contexto (PC + PSW) y salta siempre a la misma dirección. El bit de modo cambia exactamente dos veces, y nunca lo decide el programa.
- **Interrupción software vs. hardware:** mismo mecanismo, distinto disparador. La primera es síncrona y reproducible (la pide el programa); la segunda es asíncrona y no reproducible (la provoca un dispositivo).
- **API**: capa que se interpone entre el código fuente y la llamada al sistema. Lo que se estandariza (POSIX, Win32) es la API; la portabilidad es del código fuente, no del binario.
- **Modo dual:** el bit de modo lo comprueba el procesador antes de cada instrucción, y un programa de usuario no puede tocarlo. Es lo que hace que la frontera de protección sea real y no una simple convención.
